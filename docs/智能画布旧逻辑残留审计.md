# 智能画布旧逻辑残留审计与决策报告

- 审计日期：2026-08-19
- 审计范围：智能画布节点、节点迁移、参数渲染、任务执行、模型能力档案、API 配置、RunningHub、ComfyUI 与独立生成页的调用关系；普通画布退役后的残留引用也纳入复核。
- 审计方式：只读源码调用链、现有画布 JSON、路由入口、测试引用和文件引用核对
- 本轮动作：已按决策退役普通画布专属页面、样式、脚本和现存普通画布数据；智能画布公共存储、节点和平台适配保留并完成入口回归检查。

## 一、结论

当前项目不是简单存在一些“没用的旧文件”，而是同时存在四种性质完全不同的历史内容：

1. **已经影响新版运行的旧逻辑**：需要修改或迁移，不能继续让它进入新版主链路。
2. **新版仍在使用的兼容能力**：不能删除，应缩小到明确的兼容边界。
3. **仍服务独立页面或 Photoshop 连接器的公共入口**：不是普通画布专属代码，删除可能破坏现有功能；需要保留并改为智能画布来源。
4. **确认不可达、没有运行引用的备份和重复代码**：可以作为第一批低风险清理项。

最重要的判断是：

> 新版智能画布应只有一套节点契约、一套模型能力真源和一套参数提交语义；旧画布数据只能经过迁移器进入新版，不能继续和新版逻辑并列竞争。

因此，本轮只删除已确认属于普通画布专属且不再有入口的页面、样式、脚本和数据；带 legacy 的公共适配、智能画布兼容节点和独立生成页仍按调用关系保留。

## 三、决策分级

报告使用以下动作：

| 动作 | 含义 |
| --- | --- |
| 删除 | 已确认不可达、无用户数据、无运行入口，可在备份后直接移除 |
| 修改 | 功能仍需要，但当前结构会让旧逻辑影响新版，应在原位置修正 |
| 嫁接 | 旧能力有价值，应接入新版契约或迁移层，之后退出新版主链路 |
| 保留 | 当前仍有明确产品价值或真实用户入口，不应清理 |
| 待确认 | 是否保留属于产品取舍，技术上不能替用户做决定 |

## 四、需要优先处理的真实冲突

### R01：远端画布合并绕过完整迁移器

- 风险级别：高
- 建议动作：修改
- 位置：`static/js/smart-canvas.js`
- 关键函数：`loadCanvas()`、`applyMergedServerCanvas()`、`normalizeLegacySmartNode()`

**功能与作用**

`loadCanvas()` 首次加载时会调用 `SMART_NODE_CONTRACT.migrateLegacyCanvas()`，把 `smart-image` 拆成素材节点和执行节点。这个方向符合新版架构。

但是，当另一个标签页保存画布或发生 409 合并时，`applyMergedServerCanvas()` 只调用较弱的 `normalizeLegacySmartNode()`。该函数会转换 `smart-container`，却不会把 `smart-image` 拆成新版节点，只是删除少量旧字段。

**为什么会影响新版**

旧画布或旧标签页返回的 `smart-image` 可以通过实时合并重新进入已经迁移过的新版画布。结果是：首次打开时迁移正确，协作合并后旧混合节点又可能回来。

**建议方案**

远端合并前必须使用和首次加载相同的契约迁移器，并携带迁移后的连接；不能只按节点逐个做轻量归一化。服务端返回的 `node_schema_version` 低于当前版本时，前端应先迁移整个远端快照，再参与合并。

**验收条件**

- 用旧 Schema 画布和新版画布同时打开两个标签页。
- 旧标签页保存后，新标签页内不得重新出现 `smart-image`、空类型节点或旧混合节点。
- 迁移后的输入、结果连接和素材 ID 不丢失。

### R02：后端保存接口只记录版本号，不验证节点契约

- 风险级别：高
- 建议动作：修改
- 位置：`main.py`
- 关键接口：`PUT /api/canvases/{canvas_id}`

**功能与作用**

后端会根据 `migration_version` 创建迁移前备份，并更新 `node_schema_version`。这是正确的安全措施。

**当前问题**

后端随后直接保存客户端提交的 `payload.nodes`，没有检查“版本 5 的智能画布是否仍包含 `smart-image`、空类型、旧执行字段或不允许的执行节点结果状态”。

这会出现一种假迁移：画布标记为 Schema 5，但里面仍可能保存 Schema 4 或更早的数据。

**建议方案**

后端增加智能画布契约校验：

- 低版本提交先做可重复迁移或拒绝保存并要求客户端重新加载。
- 当前版本提交不得包含已经淘汰的混合节点类型。
- 执行节点、素材节点、结果素材和连接方向分别校验。
- 继续保留迁移前备份，不直接覆盖原数据。

**验收条件**

- 后端不能保存“版本 5 + `smart-image`”这种互相矛盾的数据。
- 合法旧画布仍能经过迁移打开。
- 校验失败必须写入日志并返回具体节点 ID 和字段。

### R03：新版执行节点仍能进入旧 `engine` 参数分支

- 风险级别：高
- 建议动作：嫁接后移除旧分支
- 位置：`static/js/smart-canvas.js`
- 关键函数：`renderDynamicParamsContent()`、`renderVolcengineParams()`、`renderVolcengineVideoParams()`、`renderMsParams()`

**功能与作用**

旧画布用 `engine` 区分 `api`、`volcengine`、`modelscope`、`runninghub`、`comfy`。新版架构改为平台 ID、模型能力档案和统一参数语义。

**当前问题**

参数面板仍先根据 `settings.engine` 分流。主画布中 6 个新版执行节点仍保存 `engine:"volcengine"`，所以它们会继续渲染旧的硬编码比例、分辨率、时长和布尔参数，而不是能力档案参数。

**建议方案**

增加一次 Schema 迁移：

- 图片节点：`engine:"volcengine"` 改为 `engine:"api"`，`provider_id:"volcengine"`。
- 视频节点：`engine:"volcengine"` 改为 `engine:"api"`，`videoProvider:"volcengine"`。
- 旧参数只在能力档案确认支持且新版没有用户值时迁移到 `capabilityParameters[model]`。
- 迁移完成并验证后，图片和视频执行节点不再允许进入旧 Volcengine/ModelScope 专用渲染器。
- `smart-ai-app` 的 RunningHub 参数面板和 `smart-comfy-workflow` 的 ComfyUI 参数面板仍保留，因为它们是新版节点的正式入口。

**验收条件**

- 上述 6 个节点迁移前后平台和模型不变。
- 参数界面统一由能力档案渲染。
- 用户已经选择的新参数不得被旧值覆盖。

### R04：模型能力静态档案与动态推导同时担任真源

- 风险级别：高
- 建议动作：修改
- 位置：`model_capabilities.py`、`data/model_capabilities/providers/*.json`
- 关键函数：`dynamic_profile_for_model()`、`ModelCapabilityRegistry.build_catalog()`

**功能与作用**

静态 JSON 保存有证据的模型能力；动态函数根据模型 ID 和平台规则补充模型档案。动态补充最初用于让新增模型尽快可见。

**当前问题**

当静态档案不是 `ready` 时，运行目录会用 `dynamic_profile_for_model()` 覆盖或补充。这样同一个模型的参数映射可能同时存在两份定义。

本次 AI MONEY 画幅错误就是这种结构性风险的表现之一：静态档案和动态推导对字段的理解不一致时，系统没有唯一答案。

**建议方案**

- 静态能力档案成为正式运行真源。
- 动态推导只能生成“待审核候选档案”，不得直接让模型进入严格可运行状态。
- 动态结果和静态档案不一致时，审计接口应报告差异，不能静默覆盖。
- 正式适配必须把动态规则生成的结果固化到平台档案并附证据。

**验收条件**

- 同一模型、同一节点类型只有一个正式请求映射。
- 删除动态回退后，已配置且已适配模型仍能正常显示和通过理论 dry-run。
- 未建档模型显示“待补档案”，不能伪装成可运行。

### R05：扩图仍向新版执行设置写入旧尺寸字段

- 风险级别：高
- 建议动作：待确认后修改
- 位置：`static/js/smart-canvas.js`
- 关键函数：`runGeneration()`、`withOutpaintDisplaySettings()`

**功能与作用**

旧扩图流程通过 `ratio`、`resolution`、`customWidth`、`customHeight`、`customSize` 把目标画布尺寸塞进图片生成请求。

**当前问题**

新版图片和视频请求已经改为只信任 `capabilityParameters`，但 `runGeneration()` 的扩图分支仍在临时写旧尺寸字段。这些字段现在可能被忽略，造成用户设置了扩图尺寸但模型请求没有收到；如果未来有人重新启用旧字段回退，又可能再次覆盖新版参数。

**产品取舍**

根据当前项目规则，扩图属于素材处理，不应自动成为所有图片模型的通用参数。只有模型接口明确支持扩图或画布尺寸时，才能提交对应字段。

**建议方案**

建议选择“素材处理优先”：扩图生成独立派生素材；需要模型参与时，先选择确认支持扩图的模型，再把目标尺寸映射到该模型正式能力参数。不要恢复旧 `ratio/customSize` 通用回退。

**验收条件**

- 不支持扩图参数的模型不会收到伪造字段。
- 支持扩图的模型能在 dry-run 中看到正确目标宽高。
- 原素材不被覆盖，扩图结果仍是新素材节点。

### R06：主画布尚未持久化 Schema 5

- 风险级别：中高
- 建议动作：迁移
- 位置：`data/canvases/9de75a87e01c4758add1c82dab30f121.json`

**当前情况**

主画布仍是 `node_schema_version:4`，保存数据里仍有大量旧 `ratio`、`resolution`、`videoAspect`、`videoDuration` 字段。这些字段不一定还参与新版请求，但会增加合并、复制、导入和旧分支误读的机会。

**建议方案**

完成 R01、R02、R03 后，再对主画布执行一次可回滚 Schema 5 或更高版本迁移。迁移前使用现有 `backups/canvas-migrations/` 机制备份，并输出迁移清单，不要直接编辑 JSON。

**验收条件**

- 迁移前后节点数量、连接数量、素材引用和用户文本可解释。
- 旧字段只保留在历史快照，不再留在新版执行节点实时设置中。
- 结果素材的生成信息仍完整可查看和再次生成。

## 五、高置信可清理项

### C01：`render()` 中 `return` 后的第二套旧渲染器

- 风险级别：低
- 建议动作：删除
- 位置：`static/js/smart-canvas.js`
- 关键函数：`render()`

新版渲染流程在完成节点复用、媒体状态恢复、事件绑定和小地图更新后明确 `return`。该 `return` 后还保留一整套 `world.innerHTML`、`nodesHtml` 和旧节点标题渲染代码。

这段代码在当前 JavaScript 控制流中不可达，不会被执行，也没有测试要求它存在。它会误导维护者，让人以为项目仍有两套有效渲染器。

建议直接删除不可达块，并增加测试防止 `render()` 再次出现整段 `return` 后渲染代码。

### C02：`runGeneration()` 中旧混合节点的不可达分支

- 风险级别：低到中
- 建议动作：删除或收缩
- 位置：`static/js/smart-canvas.js`
- 关键函数：`runGeneration()`

函数入口已经限制为“新版执行节点或 `smart-group`”。在这个前提下：

- `sourceVisualState` 要求当前节点同时是旧图片/素材节点，实际不可成立。
- `extracted` 初始化为 `null` 后没有赋值。
- `shouldCreateBranchOutput` 对允许进入的节点恒为真。
- `!branchNode` 的原节点承载运行状态分支实际不可达。

这些代码来自旧“素材节点既输入又执行”的架构。建议在为执行节点、分组运行、占位结果、失败和取消补齐契约测试后删除。

### C03：源码目录中的大型备份文件

- 风险级别：低
- 建议动作：删除，历史交给 Git 和 `backups/`
- 文件：
  - `static/js/smart-canvas.js.stable-before-minimax-20260804-codex`
  - `static/js/smart-canvas.js.mojibake-backup`
  - `static/js/smart-canvas.js.broken-before-stable-20260804-171031`
  - `static/css/smart-canvas.css.stable-before-minimax-20260804-codex`
  - `static/css/smart-canvas.css.mojibake-backup`
  - `static/css/smart-canvas.css.broken-before-stable-20260804-171031`

六个文件合计约 3.12 MiB，没有 HTML、运行脚本或测试引用。它们不会影响浏览器运行，但会污染全文搜索，让旧实现和当前实现混在一起。

建议确认 Git 历史和现有 `backups/` 已能追溯后删除，不再把源码备份放在 `static/` 可发布目录。

### C04：`static/js/i18n(1)/smart-canvas.js` 重复目录

- 风险级别：低
- 建议动作：删除并修改测试

运行时只加载 `static/js/i18n/smart-canvas.js`。`i18n(1)` 不被页面加载，内容也落后于正式文件；当前只有一项测试把它列入 RH 币文案扫描。

建议删除重复目录，并让测试只扫描正式运行文件。不能继续为了测试而保留一份不会被用户加载的过期文案副本。

## 六、应嫁接而不是删除的兼容能力

### A01：历史 `smart-prompt`

- 风险级别：中
- 建议动作：嫁接、迁移后退出正常运行体系
- 位置：`static/js/smart-canvas.js`、`static/js/smart-node-contract.js`

`smart-prompt` 仍拥有完整的渲染、编辑、LLM 运行、连线、分组、尺寸和计时兼容逻辑。新建菜单已经不会再创建它，而是创建 `smart-text-generator`，方向正确。

不能直接删除的原因是主画布仍有 9 个该节点，其中有真实文本和连接。

建议迁移规则：

- 只有静态文本、不调用模型：迁移为文本素材节点。
- 启用了 LLM、系统提示词或模型设置：迁移为文本生成执行节点。
- 同时承担文本内容和模型执行：拆成“文本素材 + 文本生成节点”，保留原连接顺序。
- 迁移成功后，运行时不再允许创建或编辑 `smart-prompt`，只保留旧文件导入适配器。

### A02：`smart-loop`、`smart-group`、`smart-minimax`

- 风险级别：删除风险高
- 建议动作：保留

这三类不是应淘汰的旧垃圾：

- `smart-loop`：批量、级联、变量提示词、停止和恢复。
- `smart-group`：节点组织、整体移动、布局和成员引用。
- `smart-minimax`：时间线式视频工作台、分段、参考轨道、播放、导出。

它们是新版画布仍需要的高级能力。正确做法是让它们调用新版执行节点契约，不改变其自身产品职责。

### A03：`runLegacyRunningHubWorkflowGeneration()`

- 风险级别：中
- 建议动作：保留但隔离
- 位置：`static/js/smart-canvas.js`

该函数当前仍被 `smart-minimax` 的历史 RunningHub 工作流调用。直接删除会破坏 MiniMax RunningHub 路径。

建议把它移入明确命名的兼容适配模块，只允许 MiniMax/旧工作流迁移器调用；新版 `smart-ai-app` 不得回退到该函数。等 MiniMax 迁移到正式应用 Schema 或独立工作流适配器后再移除。

### A04：结果素材中的 `runSettings`

- 风险级别：低
- 建议动作：保留数据，修改命名和边界

这部分是“生成信息快照”，不是执行节点实时设置。建议后续迁移为：

```text
generationVersions[].snapshot
```

快照应只读，包含平台、模型、运行模式、输入引用、提示词、参数、Skill/模板快照和任务引用。它不能参与当前执行节点的模型筛选，也不能被参数面板自动保存覆盖。

## 七、仍服务其他入口，当前不能删除

### K01：`/api/online-image`

- 建议动作：保留，未来逐入口迁移

该同步接口仍服务在线图片生成页。智能画布已经主要使用 `/api/canvas-image-tasks` 的异步任务接口，但这不代表同步接口是死代码。

如果未来要统一，应先让这两个调用方迁移到任务接口并完成成功、失败、取消和恢复验证，再删除 `/api/online-image`。

### K02：`/api/image-params`

该接口的比例、分辨率、质量和数量仍是一套硬编码图片参数 Schema。智能画布已经不使用它，但 Photoshop 连接器仍在真实调用。

不能直接删除。建议让该接口从模型能力档案生成 Photoshop 可渲染 Schema，保留接口形状，逐步消除第二套硬编码参数真源。

### K03：独立生成页

用户当前要求是新版架构优先，但还没有明确要求取消这些独立工具入口。建议保留，直到形成“功能迁入智能画布、旧入口跳转或下线”的产品清单。

这不是缺文件。后续应在确认所有启动脚本、打包和 Windows 路径都读取新目录后，完成一次正式迁移提交；不要同时保留根目录和 `workflows/comfyui/` 两份工作流。

## 八、RunningHub 双数据源

### D01：`data/api_providers.json` 与 `static/runninghub/api_providers.json`

- 风险级别：中高
- 建议动作：嫁接为单向种子关系
- 位置：`main.py`
- 关键函数：`load_static_runninghub_provider()`、`merge_runninghub_provider_with_static()`、`sync_runninghub_provider_workflows_to_static_template()`

**当前作用**

- `data/api_providers.json`：用户当前配置、启用模型、地区、Key 对应状态和 RunningHub 应用/工作流。
- `static/runninghub/api_providers.json`：系统模板、缩略图和历史工作流种子。

**当前风险**

保存用户配置时，部分 RunningHub 工作流又会写回静态模板；读取时两者再合并。它不是完全双向同步，但已经形成双写和覆盖关系。

这会导致：

- 用户删除的条目可能被模板重新补回，只能依赖隐藏 tombstone 阻止。
- 静态模板字段和用户字段的更新顺序决定最终结果。
- 旧工作流配置可能重新进入新版 API 设置。

**建议方案**

- 静态文件只作为首次安装和版本升级的只读种子。
- 用户配置只写入 `data/api_providers.json`。
- 系统新增条目通过带版本号的迁移合并，用户删除状态继续由稳定 ID 记录。
- 运行时不得把用户工作流写回 `static/` 发布目录。

**验收条件**

- 用户删除模型或应用后，刷新、重启、升级都不会自动补回。
- 更新系统种子不会覆盖用户字段、排序和启用状态。
- Git 工作区不会因为用户操作而修改 `static/runninghub/api_providers.json`。

## 九、已修复但应保留回归测试的冲突

### F01：旧画幅字段覆盖新版能力参数

新版 `capabilityParameters.aspect_ratio` 曾被旧 `ratio`、`videoAspect` 回退值覆盖，导致用户选 16:9 仍可能生成 9:16 或其他比例。

当前已改为：图片、视频正式请求以当前模型的能力参数为唯一来源；节点 Schema 5 会清理图片/视频执行节点上的冲突旧字段。

必须长期保留以下回归：

- 用户选择的画幅、分辨率和时长进入 dry-run 标准请求。
- 旧字段存在时也不能覆盖新版值。
- 模型未选择参数时按“使用默认”不提交字段。

### F02：AI MONEY 低价图片模型尺寸字段映射错误

`laohuaimoney-image-g-v2-lowprice` 曾把画幅错误映射到不存在的 `ratio_or_size`，官方接口实际要求顶层 `size`。

当前已修正为：

- `aspect_ratio` 映射到 `size`。
- `resolution` 映射到 `metadata.resolution`。

该问题再次证明 R04 的必要性：正式请求映射不能同时由静态档案和动态猜测共同决定。

## 十二、完成标准

后续实施不能以“删了多少旧代码”为完成标准，而应满足：

1. 新版执行节点不会再读取旧混合节点参数作为运行依据。
2. 任何旧画布进入新版前都经过同一迁移器。
3. 后端不会保存节点版本与节点内容互相矛盾的数据。
4. 每个模型只有一份正式能力和请求映射真源。
5. 用户文本、素材、连接、生成历史和个性化设置不因迁移丢失。
6. 智能画布和独立生成页面继续正常工作；普通画布专属入口不再提供。
7. 清理项不改变当前智能画布界面、节点位置、参数值和正常运行功能。
8. 每批修改都通过定向测试、全量相关测试和真实浏览器回归后再进入下一批。

一句话总结：先切断旧逻辑影响新版的通道，再迁移有价值的历史数据，最后删除真正不可达的残留；不能把“旧”简单等同于“无用”。
